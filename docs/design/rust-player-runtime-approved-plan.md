# 単一Pythonプロセス＋Rustプレイヤーランタイムの実装計画

`feat/ppo-shared-inference` の `9680f06` を基点に、全試合のプレイヤー処理を同一プロセス内のRustランタイムに集約する。**A「1試合1 Tokioタスク」とB「固定Rustワーカーへの試合割当」を実対戦で比較し、採用候補をHPO Model4と通常PPO Model3の学習・保存・再開まで通す。** 正しさを満たし、現行と同等以上の速度でメモリが減った場合に、新規CUDA MLP学習の既定へ切り替える。[実装前調査](</home/percy/develop/GodFieldBots/.worktrees/ppo-shared-inference/docs/design/rust-player-runtime-research.md>)・[Tokio／PyO3の比較条件](</home/percy/develop/GodFieldBots/.worktrees/ppo-shared-inference/docs/design/rust-player-runtime-tokio-pyo3-notes.md>)

## 1. 実行構成とインターフェース

| 担当 | 実装する責務 |
| --- | --- |
| Rustの試合ランタイム | 外部SimulatorとのHTTP v2通信、試合イベント配送、参加者別の観測・履歴・候補生成、行動選択の管理、Act送信とACK照合 |
| Python／PyTorch | 1つの学習ホストで、既存MLPの推論、参加者別Torch RNGによる抽選、PPO更新、モデル保存・復元を実行 |
| 保存担当 | 同じPythonプロセスの専用スレッドでSQLite接続を所有し、既存の記録・検証・封印処理を再利用。試合処理とは容量制限付きキューで接続 |
| Rust監督プロセス | 学習ホストを起動し、元のプロセスハンドルで終了を確認。HPOでは既存のGPU入場管理と同じ名前空間で、異常終了と回復に必要な証跡を保持 |

- 新しい実行モードに `game_concurrency`、`player_worker_threads`、`max_batch_size`、`formation_wait_ms` を持たせる。`player_worker_threads` はプレイヤー処理を実行するRustスレッド数。I/O、保存、PyTorchのスレッド数は別に記録する。
- バッチ形成はRust側の1か所で行う。最初の有効要求からの絶対締切、またはバッチ上限への到達で発行する。Pythonには `next_batch()` と `submit_results()` に相当する境界を設け、待機中はGILを解放する。初版はこの同期境界を専用担当から使い、PythonのasyncioとTokioを統合する依存は追加しない。
- 実行・試行ID、実際のSimulator game ID、player IDでプレイヤー状態を所有する。各試合の状態変更は直列化し、未完了の推論は1試合1件とする。方策traitへは本人の入力だけを渡す。応答の要求ID・revision・checkpoint・期限を照合し、失効した応答からRNGを進めたりActを生成したりしない。
- Simulatorは既存の外部バイナリを使用する。初回の対象はMLP学習で、GRU・TransformerとHPO評価ランタイムの移植は後続とする。既存の評価に渡すモデルと親データの適格性は引き続き検証する。

## 2. 実装順序

1. **設計レビューと比較原本を先に作る。** Rootが所有権、失敗境界、設定・証跡の版、依存変更を設計書とADR案にまとめ、実装前にアーキテクチャレビューを通す。現行v5生成器から、本人入力・固定探索時計・RNG前状態・候補順・table hash・選択・RNG後状態を記録した比較ケースを作る。旧生成器用goldenはその版のまま保持する。
2. **Rustのプレイヤー処理を移す。** Random、Heuristic、Refresh、MLPに必要な候補生成・状態管理を実装する。Python `random.Random` の使用箇所はseed導出、shuffle、`randrange`、状態記録を含めて互換にする。MLPの抽選には参加者別のCPU `torch.Generator` と既存の `torch.multinomial` を使う。Rustが要求の有効性と抽選結果の採用を管理し、遅延応答で参加者の乱数列がずれないことを試験する。
3. **共通の推論経路を作る。** Rustから最終dtype・形状のバッファと行ごとの長さを公開し、PythonでCPU Tensorとして参照する。既存の行単位スコア計算と不変checkpointレジストリを再利用する。CPU上の共有、バッチ組立、H2D、GPU演算、返送を個別に計測する。最後のTensor参照と非同期転送が終わるまで領域を再利用しない。
4. **同じ処理にA/Bのスケジューラを接続する。** Aは試合ごとのTokioタスクを設定数の実行スレッドで駆動する。Bは試合を固定ワーカーへ割り当て、HTTP・推論の完了イベントで再開する。どちらも応答待ち中に他試合を進め、同じHTTPクライアント、候補生成器、推論器、時計、保存担当を使う。Rayonとの併用は、CPU探索がイベント配送を阻害すると実測できた場合の後続候補とする。
5. **保存と学習を一体化する。** Act前のpending記録と、ACK照合後に確定する経験を区別する。保存担当が不変データとメモリ予約を引き受けた時点で試合枠を解放し、容量不足時は新規試合の受付を抑える。収集の確定、PPO更新、checkpoint保存・commit、次世代公開の順序を守る。保存やGPU処理が失敗した親には失敗を記録し、再開は確定済みの更新境界から行う。
6. **通常の学習入口へ接続する。** Model3は既存の `gf-bots train`、Model4はHPOの学習操作から同じRustランタイムを使う。新しい実行モード・終了証跡・producer identityを明示的に版管理する。正常終了ではタスクのjoin、バッファ解放、保存確定、GPU利用終了を照合する。強制終了ではRust監督が実際に確認できた終了状況を記録する。

## 3. 正しさと障害時の受入試験

- **方策互換。** 固定入力・固定探索時計・同じseedで、候補内容と順序、選択、RNG後状態を現行と一致させる。防御、Refresh、同一カード複数、空イベント、MP依存武器、候補数の大きい判断を含める。実時間制限による探索打切りは、実対戦で理由・頻度・候補数を比較する。
- **論理分離。** 同一試合の別席、別試合の同じ席、別試行で再利用したIDについて、他の要求の値・長さ・処理順を変えても基準席の出力と抽選が変わらないことを確認する。単独推論とのFP32比較は既存の `atol=rtol=1e-5` を使う。
- **並行処理と終了。** 2試合・4参加者をW=1とW=2で動かす。満杯のキュー、期限切れ、同一command IDの再送、遅延ACK、GPU応答待ちでの取消、writer障害、強制終了を注入する。二重Act・二重学習・早すぎるバッファ解放を検出し、終了通知を待つ試合が取り残されないことを確認する。
- **学習と再開。** HPO Model4と通常PPO Model3のそれぞれで、CUDAの連続2更新と、1更新後に停止して再開する2更新を比較する。G0受付後のG1公開、凍結G0の利用、optimizer・RNG・スケジュールの復元、元記録・Replay・数値データの独立監査を通す。実際のプロセスツリーで、学習中のPythonプロセスが1つであることも確認する。

## 4. 性能比較と既定切替

- **第1段階は8試合同時。** C8/B8でA・BそれぞれのWを1・2・4・8とし、現行方式の対照を前後に置く。各走は既存比較と同じ幅192、seed 17、4 epochs、minibatch 128、32試合×2更新。形成待機は全方式1 msに固定する。各方式から収集速度が最も高いWを選ぶ。速度差が3%以内ならピークPSS、続いて小さいWを優先する。
- **第2段階は16試合同時。** C16/B16で各方式の候補と現行方式を同じ条件で比較し、逆順でもう一度測る。16並列は過去に記録用4 GiBで停止したため、全方式に5 GiBを明示する。全体上限はRAM 24 GiB・CUDA 12 GiB。失敗した走は理由とともに保存し、完走した母集団に混ぜない。
- **測定項目。** 試合/秒、全参加者decision/秒、学習実行全体の経過時間、実効バッチ分布、イベント待ちと推論往復のp95/p99、PyO3呼出回数、CPU使用率・スレッド数、GPU転送・演算時間、PSS、保存キューの滞留量・待ち時間。初回と第2収集を分け、生成された候補数や探索打切りの変化も併記する。
- **既定切替。** 正しさ・再開・監査を通った方式について、実際に配布するHPO C4/B4と通常PPO C2/B2でも、現行と新方式を交互に各2走確認する。この計画では「速度維持」の判定幅を事前に**3%**と置く。対応する対照に対して収集速度の低下と学習全体の時間増加がともに3%以内で、両回ともピークPSSが低い場合に、その入口の新規CUDA MLP学習の既定を切り替える。判定が割れた入口は明示指定で提供し、既存プリセットと既存親のresumeは記録済みの方式に従う。

実装は `9680f06` から専用ブランチで進める。設計、互換性、単一プロセス学習、実測・導入を個別にレビューできる単位でコミットし、独立した正しさ・設計適合レビュー後に、採用方式・W・実測値・残課題をそろえてマージ前に引き渡す。
