# 通常のHPO6収集でRustのJournalライターを使う

現行のSacrifice CardInstance契約、MLPのネイティブPPO Source、HDD保存用のtmpfsステージングを使うHPO6で、全試合を一括投入できる場合に適用する。参加者は検証済みのMLP、既存のRandom、Heuristic、Refreshに限る。ゲーム進行・記録のワーカーは、既存設定の `player_worker_threads` と同じ数を使う。Simulator 6d50603、Journal6、候補表codec2、GroupPack v1、HDD保存とSourceの既存形式を引き継ぐ。

収集所有者が実行済みSimulatorのreceiptと計画を結び付ける。Rustの単一Mailbox readerが原本と同じArcを保持し、準備済みの別試合の原本を並列に検証する。元のFIFO順を維持して、検証し終えた不変原本に受付を返す。処理期限や原本に不一致があれば既存の失敗経路で終了する。試合が終わると生成済みのJournal、候補表と利用可能なReplayをペアの保存担当へ渡す。

原本のシリアライズが使う一時バッファは、Mailboxの記録台帳で割り当てた容量を実際の解放まで計上する。一時領域だけが通常予約を妨げる場合は、通常予約を優先し、一時領域の返却時に再判定する。確保を断られたシリアライザは一時領域を返してから実長を計測し、同じ記録予算の通常予約で書き直す。送信側は元の受付期限を引き継ぐ。候補表の部分読み込みでも原本全長のJSON予算、予約キー検査、文書末尾の検査を維持する。検索報告の照合に続いて、同じ原本の全候補を型付きで検証してから受付を返す。

ゲームが作られなかった場合は既存のterminalと空のイベントバンクを残す。打ち切り、異常終了、取消しでは、元の報告・実際に得られたReplay・元のイベントの末尾を残し、未ACKの判断をJournal終端に記録する。自然終了でもcleanup等の問題がある場合は既存Journalの自然終了内容を維持する。学習行の証拠はエラーなし、cleanup完了、推論の退役済みの自然終了だけで作る。HDDでの公開、正式Sourceの資格、PPOの受付条件は既存の所有者が管理する。

現行のサポート範囲外では既存経路を使う。保存済みrunの再開は記録された同一のproducerを必要とする。新しいwheelは新規runと同じwheelで停止したrunに使う。途中失敗やcancelで未確定Sourceの発行を許さない。ワーカープール・原本・出力の所有は実際の読取担当と保存担当の退役まで保持する。

試合終了後の結果コントロールは、既存のRecordingArtifactsのバイト列を一括でライターへ渡す。DB所有スレッドが元DBと期限を照合し、内容を単一トランザクションで保存する。書き込みの終了を確認するまで、呼び出し側が予約を保持する。HDDへの公開処理では監査と非公開ファイルの同期を回収し、書き込み直後のファイル状態と照合してから既存の公開順を進める。 [耐久公開の条件](../adr/0065-staged-native-collection-storage.md)

型付き引き渡しの有効化権は実際のネイティブWriterが保有する。Actorが原本JSONの直列化と受付の両方に同じ不変データを使い、Mailboxに入る型付き情報は一度限りの弱参照とする。読取側は従来の予算で借用し、検証、Journal行生成、領域確保を終えてからACKする。Actorが退役して借用できない場合や汎用Python経路では、原本バイト列で同じ検証を行う。固定の定義ピンとACK検証レシピは、収集に必要な既存の不変データから借りる。

全試合を一括投入するネイティブJournalの読取担当は、終端ACKごとに対象のチェックポイント参照の識別子を控える。最終ACKの後、対応する推論ルートが退役してから共有Torchロックの下で解放する。実行期限はロック取得にも適用する。解放に成功した各参照を所有表から取り除くため、途中で失敗した場合はjoinが残りの参照だけを回収する。読取担当と解放の完了は正式Source発行の前提である。

試合コンテキストでは、同じ方策ラベルから導かれる容量・コスト設定を収集内で再利用する。全試合の一括投入時は、同じ実行レシートと起動情報を持つ隣接2試合が検証済みの公開カタログを共有する。共有の所有期間はその2試合に限る。カタログの参照は対戦中の当事者に見える定義に対して行い、接続、作成、参加の確認は各試合が担当する。
