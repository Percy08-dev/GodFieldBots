# 0075 通常のHPO6収集にRust Journalライターを採用する

状態はAccepted。設計・実装レビューと通常環境での確認を通過した。

## 背景

[ADR0060](0060-rust-player-journal-handoff.md) は各原本をPythonのwriterへ引き渡し、検証済みの受付をRustに返す。直近のMLPの256試合では、ライターと推論スレッドのGIL競合があり、ゲームがAct前後に記録の受付を待つ間に推論リクエストの供給も止まっていた。同じ記録をRustで生成する試作は、実同時256試合で16記録ワーカーの380.08 actions/sを計測した。

## 決定

HPO6のRust PPO Sourceを使うMLPで、現行Sacrifice CardInstance契約、tmpfsからHDDへの保存、全試合の一括投入を満たす場合にRust Journalライターを使う。参加者はMLP、Random、Heuristic、Refreshを対象にする。記録用のワーカー数は既存の `player_worker_threads` から取る。対象外の構成と履歴の検証には従来の経路を使う。

Rustの読取担当は検証済みの同じ原本を保持し、準備済みの別試合の原本を並列に検証する。受付時に全件の原本と期限を照合し、元のFIFO順で受付を返す。打ち切りや異常終了でも、未ACKの判断、入手したReplay、イベントバンクと終了理由を保持する。学習用の証跡は既存の正常性条件を満たす自然終了に限って作る。

原本のJSONはRustの送信側で原則1回シリアライズする。拡張中の新旧バッファを同じ記録予算に計上し、一時領域が通常予約と競合したら解放して実長計測に戻る。公開するバイト列と保持する予約は原本の実長にそろえる。原本を解析する経路では、検索報告の照合に必要な候補表の項目だけを汎用JSONに展開する。同じ原本に対して従来の型付き全候補検証とハッシュ照合を受付前に行う。

実際のRust Journalライターは、Mailboxから排他的に型付き引き渡しの有効化権を取得する。ActorはpendingとACKの不変データを保持し、同じデータを原本JSONに直列化する。Mailboxには原本バイト列と、そのデータへの一度限りの弱参照を渡す。受信側は元のJSON予算で一時的に借り、原本全体の再解析を省いて検証する。弱参照が失効した場合は元の厳格な原本パーサーを使う。Frame、Delta、選択・乱数状態、ACK、候補と行動の検証、Journal行の生成と領域確保、原本SHA・順序・期限の確認は受付前に行う。

Writerの退役はコンテキストを確認し、実ワーカーのjoinを終えてから有効化権を返す。退役済みWriterの読み取りや登録はそのWriter自身の権限で拒否する。汎用Python経路へ原本を渡す前に弱参照を取り除く。候補表やフレームの型付きデータは確定済み原本と重複して保存しない。ネイティブ経路のフレーム検証では同じ組み込みピンを参照し、ActのACK検証には既存の固定ウィンドウ16のレシピを借りる。個々の定義、フレーム、イベント、観測、ヒントの検証は従来どおり行う。

SQLiteへのコミット、HDDへの耐久公開、正式Sourceの発行は既存の所有境界を通る。SQLite投入とHDDでの独立監査では、各Packをそれぞれ1回展開し、展開したバッファの範囲を直接ハッシュして、実長と全メンバーの索引を検証する。HDD監査のSQLite整合性、外部キー、コピー先DBのSHA-256と同期を維持する。Rustの検証と重なる展開用バイトは既存の共有作業枠に計上する。

固定ウィンドウ16のイベントレシピとcodec2のコードブックのハッシュは、最初の試合コンテキスト登録時に一度作り、収集内で共有する。各原本の検証と各試合の期限は維持する。正常・異常のどちらでも読取担当とwriterの退役を確認して、共有レシピと作業枠を返す。Journal6、候補表codec2、GroupPack v1、Sourceと保存済みproducerの同一性照合を維持する。

収集計画を組み立てる際は、実際に使う方策ラベルごとにワーカーの容量と数値コストを一度だけ検証する。各席のコンテキストは、その席の乱数seedと個別の設定辞書から作る。

全試合を一括投入するRust Journal経路では、Simulator起動と実行ファイルの照合を既存の `player_worker_threads` を上限に重ねる。イベントループが各Serverと実行前receiptの所有権を管理する。照合ワーカーがPID、起動時刻、実行ファイル全体のSHA-256を照合し、イベントループで同じProcessの生存と期限を確認する。起動・照合が実際に終了してから、元の計画順でwriterを登録して一括投入する。取消時は実行中の照合を回収し、確認済みreceiptを元の後始末に渡す。

同じ収集の計画順で隣接し、同じrun・trialとSimulator起動情報・実行レシートを持つ2試合は、固定ハッシュを照合済みの `public-ja-v3` カタログを共有する。各試合は自身の接続、Create前の公開メタデータ、Join前の接続を個別に確認する。共有待機には自身の実行期限を適用し、実際のGETは通常のHTTP期限と診断を使う。取得失敗や取消時は、もう一方の試合が自身の接続から取得できる。

このステージング経路では、終了結果の `result.json` を既存のライターに一括で渡し、既存と同じコントロールBLOBを一つのSQLiteトランザクションに保存する。名前、サイズ、メンバーとの衝突、同一内容の再送を行ごとに検査する。終了結果が保存できた後に従来の収集報告とmanifestを作り、同じ所有者でsealする。HDD公開前に独立監査とファイル同期を重ね、両方の完了後に書き込み直後のファイル状態を照合する。 [耐久公開の条件](0065-staged-native-collection-storage.md)

全試合を一括投入するRust Journal経路では、各試合のネイティブ終端ACKを確定した後、チェックポイントの参照解放を最終試合の終端ACKまで延期する。対象の推論ルートが退役してから、既存の実行期限内に共有Torchロックを取り、参照をまとめて解放する。記録の検証、領域確保、受付順序と期限は従来の処理で適用する。解放に失敗した場合は正式Sourceを発行せず、残りの参照はjoin時の後始末が回収する。

詳細は [設計](../design/rust-rollout-journal-adoption.md) に記録する。

## 検証

- Rustの関連テスト24件とPythonテスト91件が通過した。Pythonの実Simulatorテストにはゲーム未作成、0行動、未ACK、手数による打ち切り、タイムアウトが含まれる。
- 通常の環境で全256試合を2回収集し、315.05と381.80 actions/sでHDD保存・正式Source・PPO更新を完了した。両回の実同時数の確認下限は255試合。切り替えの確認用作業ツリーでは同時256試合を確認した。
- 5,081行動のJournalの照合結果と更新後の重みは対照と一致した。16試合の新規runは、2回目の更新への再開とJournal・Replay・Python数値の独立監査を通過した。
- JSONの1回シリアライズと候補表の部分読み込みを通常のwheelで有効にした。変更後は256試合、5,081行動、記録ワーカー16で364.48と378.92 actions/sを計測し、両試行でHDD保存、正式Source、PPO更新を確認した。HTTPログから確定できた実同時稼働数の下限は255試合だった。
- 採用版はRustテスト30件とPythonテスト91件を通過した。同じwheelで停止した16試合のrunを再開し、2回目の更新までのJournal・Replay・学習データを完全監査した。
- 別の計測用wheelで同じモデルとseedを使い、採用前後を各2回計測した。採用後の3,936推論要求ではキュー滞留のp95が329〜355ms、バッチ取り出しから結果受理までのp95が63〜76msだった。開始7秒までに投入された要求のキュー滞留p95は359〜398ms、推論区間末尾2秒の投入では11〜12msだった。採用前のキュー滞留p95は330〜352msだった。詳細トレースは隔離した診断用wheelだけに含めた。
- 最新経路の比較では全256試合と5,081行動を維持し、通常351.78〜364.22、圧縮・永続化だけを外した診断440.28〜455.60、Journal原本生成・受付をさらに外した診断644.26〜657.13 actions/sを記録した。省略条件の分母は試合と記録担当の退役時点まで。Pack検証とレシピ共有は通常保存付きで個別に比較し、併用で405.00〜405.94 actions/sだった。Simulator起動と照合を重ねた試作は440.94〜452.78 actions/sで、実同時256を確定できたのは440.94の試行だった。
- 採用した最終版は、計測用の処理を外した通常環境で実同時256試合を2回確認し、収集時間10.858秒と11.191秒で467.93と454.01 actions/sだった。両試行で5,081行動と更新後の重みが対照と一致し、保存データと正式Sourceを照合した。同じproducerで停止した16試合のrunは、再開して2回目の更新までのJournal・Replay・学習データの完全監査を通過した。
- 終端結果の一括保存を試したとき、256件の生成・書き込みは約0.22秒から0.011〜0.012秒に短縮した。型付き候補表の引き渡しは全5,081件で動作し、Journal・PPO用データも照合できたが、受付時間の安定した短縮が得られず隔離試作に留めた。
- 一括保存とHDD監査・同期の並行化を適用した版では、実同時256試合を2回確認し、447.74と467.58 actions/sだった。HDD保存、正式Source、PPO用データ、更新後の重みを検証した。16試合で停止と再開を行い、同一producerで2回目の更新を完全監査した。非公開ファイルの破損・復元を再現する試験では、DBと記述子のどちらも公開前に拒否した。
- 型付きpending・ACKと固定検証データの再利用を両方有効にした計測版は、5,081行動の実同時256試合で483.50と480.77 actions/sだった。16ワーカーで一度に取り出す上限を32件へ広げる試作は、同じ配布物の比較で全体を短縮できなかった。
- 計測フラグを外した同一producerの通常版では、実同時256試合を確認できた2回が494.80と484.14 actions/sだった。前者は照合済みwheelの確認用作業ツリー、後者は通常作業環境で実行した。5,081行動のJournalとPPO入力・更新後の重みを対照と照合し、16試合の停止・再開の独立監査を通過した。550 actions/sまでの差は最速試行で1.03秒だった。
- 参照解放の一括化は、同じ通常wheel、モデル、seed、初期重みとHDD保存条件の追加対照3組で、5,081行動の収集をそれぞれ1.06秒、0.75秒、0.52秒短縮した。中央値は473.93から509.67 actions/sに改善した。2組目は両試行で実同時256試合を確認し、残り2組のログ上の下限は255試合だった。直前の対照2組では約0.05秒ずつ悪化しており、5組全体の収集短縮は中央値0.52秒だった。旧経路と採用経路でJournal、正式SourceとPPO入力を照合し、更新後の重みが一致した。
- 方策ラベルごとの設定再利用とカタログのペア内共有を適用した通常版は、5回の中央値が547.14 actions/sだった。実同時256試合を確認した3回が518.16、558.71、547.29 actions/sで、550超は1回だった。設定再利用だけを対照とした追加2組では、5,081行動の収集を0.29秒と0.24秒短縮した。各試行の128ペアすべてでカタログGETが1件、個別の接続確認と試合作成・参加が成立した。HDD保存、正式Source、PPO入力と更新後の重みを照合した。16試合の停止・再開では2回目の更新までJournal、Replay、数値の完全監査が通過した。
