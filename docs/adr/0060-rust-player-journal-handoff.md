# 0060 Rust playerのJournal引き渡しと全試合の一括投入

状態はユーザー承認済み、実測と実装レビューを進行中。

## 背景

256試合の計測では、RustのJournal登録から取り出しまでのp95が
約0.9秒だった。Pythonの試合管理ループは各レコードの取得、writer受領、
Rustへの確認応答を個別のexecutorジョブで待っていた。
連続取り出しのPoCでは、同時256試合でModel 3が9.0%、
Model 4の逆順再比較が9.3%短縮した。
また通常PPOとHPOの共通経路はペアの2試合を順次起動していたため、
256試合の収集では128グループが実際の同時進行数の上限になっていた。

## 決定

- 共通の試合管理ループは、収集ごとに単一のexecutorジョブでRustのFIFOを取得する。
  同じ元レコードを既存のwriterが検証・受領した時点で既存のRust確認応答を返す。
  収集の監査に使う受領リストをFIFO順に積み、terminal完了だけをイベントで管理ループへ通知する。
  管理ループがSimulatorの起動と停止を担当する。
- writerの受領、グループのSQLite確定、全体のseal、学習結果のcheckpoint公開は
  それぞれ既存の完了条件を使う。障害時は既存の取消経路で待機を解除し、
  元の取り出し担当の終了を確かめてから既存の後始末を行う。
- 収集の全試合が設定された同時実行上限に収まる場合、既存の
  Repeated seedの各グループ用Simulatorを起動する。現在のレシートとwriter
  コンテキストを登録した後、計画順の全試合を一括投入する。
  収集が上限を超える場合は従来のペア内順次起動を使う。
  ペア内の全試合のterminal確認応答後に、そのSimulatorを停止する。

## 根拠と比較対象

Pinned Simulator `072dabbca1458c9526897781d2fd64edeeb4f9ca` の
CLI仕様と試験要件では、Repeated seedの払い出しは同一seedを返し、
各GameとHeaderは独立した識別子を持つ。同じ初期状態からのペア比較は
Createリクエストの到着順に依存しない。起動順序だけを変更し、
seed、席割当、実行レシート、記録形式、参加者の情報境界を引き継ぐ。

executorジョブを1件1回にまとめる案もPoCで改善した。
連続方式はその案から各モデルでさらに0.85〜1.21秒短縮した。
受領済みの順序リストとイベントを再利用することで、Journalの
レコードキューを増やさずに、Simulator停止中も他の試合の取得を進められる。
収集が上限を超える場合に一括投入を広げるには、Simulatorの
資源所有と起動枠の設計を改めて評価する。

## 検証

通常PPOのModel 3とHPOのModel 4について、実同時256試合で
Journalだけを変えた各3回の交互A/Bを行う。
試合の一括投入の効果は連続取り出しを両条件に適用して別に比較する。
順序、途中の失敗、取消、原本・Replay・FP32結果の一致、
保存後の再開と2回目の収集・更新を確認する。
