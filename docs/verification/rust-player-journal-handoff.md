# Rust playerのJournal連続取り出しと一括投入

設計は [ADR0060](../adr/0060-rust-player-journal-handoff.md)。
コードはJournal連続取得の `27f500f` と一括投入の `2d40465` に分けた。
通常PPOのModel 3とHPO6のModel 4は同じ試合管理コードを通る。

## 測定条件

Simulator `072dabbca1458c9526897781d2fd64edeeb4f9ca`、RTX 5070 Ti、
CPython 3.14.10、Torch 2.14.1+cu132。学習seedは17。
Torch推論は1レーン、形成待ち1ms、幅32、worker16、128MiBの一時領域上限と
固定1形状のGraphを使った。収集時間は通常の準備・退役を含み、PPO更新を除く。

Journalの比較では、旧方式にも同じ条件で全試合を投入する計測用の起動順序を
適用し、PPO設定と初期checkpointを固定した。既存の軽量テレメトリを使い、
詳細トレース、CUDA Event計測、カーネルプロファイラを外して交互に測定した。
HTTPログで256試合の同時稼働を確認できた各3回を採用した。
保守的確認下限が255だった旧方式のModel 4初回と、新方式のModel 3の
2回目は取り直した。初回PoCのModel 4の63.59秒は今回の比較に入れていない。

## Journal変更単体

| 指標 | Model 3 旧 → 新 | Model 4 旧 → 新 |
| --- | ---: | ---: |
| 収集秒、各3回の中央値 | 49.89 → 44.35 | 53.64 → 49.14 |
| 試合/秒 | 5.13 → 5.77 | 4.77 → 5.21 |
| Rust Journalキュー待ちp95の中央値 | 864 → 646ms | 931 → 747ms |
| Rust Journalキュー最大の中央値 | 239 → 225件 | 235 → 220件 |
| 収集あたりの推論供給 | 77.40 → 87.05件/秒 | 75.75 → 82.69件/秒 |
| forward数 | 1,312 → 841 | 1,319 → 834 |
| 有効要求数/forward | 2.94 → 4.59 | 3.08 → 4.87 |
| 推論スレッドの次バッチ取得Wall | 13.49 → 9.08秒 | 16.35 → 10.45秒 |
| 収集中のPythonホストCPU | 74.73 → 65.78秒 | 79.39 → 72.93秒 |
| 観測されたPSSピーク | 3,255 → 3,235MiB | 3,330 → 3,270MiB |
| Torch予約ピーク | 350 → 366MiB | 416 → 442MiB |

CPUはプロセスのtickサンプル、PSSは完全な観測スイープのピーク。
次バッチ取得Wallには形成待ちとPyO3の復帰も含まれる。
キュー待ちp95は既存ヒストグラムの上下限の中点の中央値。
数値、条件、監査ファイルの位置は `runs/journal-production/report.json` にある。

## 試合投入順序の変更単体

Journalを新方式に揃え、従来のペア内順次の実同時128試合を各モデルで1回測定した。
採用後の実同時256試合の中央値との比較を以下に示す。

|  | Model 3 128 → 256 | Model 4 128 → 256 |
| --- | ---: | ---: |
| 収集秒 | 44.93 → 44.35 | 49.53 → 49.14 |
| forward数 | 948 → 841 | 1,015 → 834 |
| PSSピーク | 3,110 → 3,235MiB | 3,126 → 3,270MiB |
| Torch予約ピーク | 350 → 366MiB | 388 → 442MiB |

128側が各1回のため収集時間差の再現性は未確認。
設定した同時実行数が、全試合を投入できる収集で使用されることを確認した。

## テストと監査

- 実スレッドを使う終了通知、writer受領前のACK防止、障害原本の保持、
  取消の再送とreaderの終了、全試合の投入と逆順のterminal処理を確認した。
- 関連の標準テストは53件成功、17件スキップ。
  [既存のfixture不足4件](../issues/0012-rust-player-collector-cleanup-fixture.md)
  を対象外として実行した。スキップにはローカルの別名Simulatorバイナリを必要とするケースを含む。
- A/Bと投入順比較は、実収集の標準監査および試合・席・手単位の
  選択行動、FP32 log probabilityとvalueの一致を確認した。

通常PPOとHPOの保存・再開検証では、各16試合の第1収集と更新を実行して停止し、
同じ保存済み親から再開した。再開後の16試合は別バッチで自然終了し、
各バッチで同時16試合を確認した。保存されたoptimizerステップ数は
Model 3で16→28、Model 4で12→20だった。
両世代の完全なJournal・Replay・Python参照数値監査が通過した。
通常PPOは第2更新の確定後にG1の5ファイルを保持方針に従って退役させ、
元の世代レコードのSHA-256と実際の退役レシートが一致した。
HPOのG1は6ファイルとも同じSHA-256で保持された。
証跡は `runs/journal-production/resume-model3/verified.json` と
`runs/journal-production/resume-model4/verified.json` にある。

## 残る待ち時間

詳細トレースの別試行はModel 3が44.57秒、Model 4が49.50秒で、いずれも
同時256試合。writerの実処理は35.58／39.87秒で、Rustキューが非空の間の
writer空待ちは3.97／4.22秒だった。最大の内訳はpendingの検証・エンコードで、
Wall時間30.43／34.32秒のうちスレッドCPU時間は29.93／33.91秒。
この処理はGPU推論と重なるため、その累積時間を収集時間の短縮見込みには使えない。

5〜20秒は推論用のキューが滞留し、推論経路が14.72／15.00秒稼働した。
Eagerがforward呼び出しWall全体の約95%を占め、累積19.94／21.77秒だった。
30秒以降の推論側の空待ちは5.01／7.46秒。30〜35秒の平均キュー長は、
推論が3.3／7.9件、Journalが112／144件だった。同じ区間でwriterは両モデルとも
約4.5秒動作していた。序盤はEagerのホスト投入とCUDA区間の切り分け、
後半はpendingの検証・エンコード内訳の計測を優先する。
時間帯ごとの重なりは `runs/journal-production/diagnostic-report.json` にある。

## 形成待ちの再評価

Model 4の同時256試合で、4msと8msを各1回計測した。

| 形成待ち | 収集秒 | forward数 | 有効要求数/forward |
| --- | ---: | ---: | ---: |
| 1ms、各3回の中央値 | 49.14 | 834 | 4.87 |
| 4ms | 49.08 | 771 | 5.27 |
| 8ms | 49.10 | 768 | 5.29 |

形成待ちを延ばすとforward数は減ったが、収集時間差は1msの反復のばらつきより小さい。
1レーン・1msを維持する。この再評価ではModel 3の4msと8msを追加計測していない。
