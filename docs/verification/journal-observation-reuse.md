# Journalの観測検証を同一レコード内で再利用

ライブwriterは、原本の観測を独立に検証して得た所有済みコピーを、
同じ呼び出し内のActionOptions照合に使う。検証は観測と候補の所有者、
revision、choice、自己カード参照、知覚定義と候補集合を照合する。
返却する観測とActionOptionsは入力から独立したコピーを持つ。
公開されたActionOptions入口は受け取った観測を検証し、
Replayは中断時の観測も含む既存の自身の検証を通したうえで全体をコピーする。
可変オブジェクトをレコード間で共有しない。

## 試合収集

基準はBots `8ac7b1e`。Simulatorは
`072dabbca1458c9526897781d2fd64edeeb4f9ca`、Journal v6、候補列codec2。
RTX 5070 Ti、Torch 2.14.1+cu132、Python 3.14.10を使用した。
Model 3は通常PPO、Model 4はHPOの収集入口。モデルごとに同じ初期重みと
seed 17を使い、実同時256試合、1レーン、形成待ち1ms、Tokio worker 16、
GPU幅32、一時領域128MiB、既存CUDA Graphを固定した。

プロファイラなしでA→B、B→A、A→Bを実行した。各組の収集時間はModel 3で
30.516→29.389、30.017→28.701、29.674→28.889秒、Model 4で
31.729→30.415、31.861→30.341、31.422→30.248秒。
Model 3の実同時255試合の4試行は集計から除き同じ条件で再測定した。
実同時数はSimulatorのJoin成功応答から終局Action到着までの区間の重なりで確認した。

| 中央値 | Model 3 A→B | Model 4 A→B |
|---|---:|---:|
| 256試合収集時間 | 30.017→28.889秒（3.76%短縮） | 31.729→30.341秒（4.38%短縮） |
| 試合数/秒 | 8.53→8.86 | 8.07→8.44 |
| Journal登録から取り出しのp95 | 398→398ms | 390→407ms |
| Journalキューの最大件数 | 229→226 | 219→225 |
| 有効推論要求/秒 | 128.63→133.65 | 128.05→133.91 |
| forward回数 | 901→905 | 911→931 |
| 有効要求/forward | 4.29→4.27 | 4.46→4.36 |

各モデルで全試行の推論要求数が一致した。登録から取り出しのp95は
pending、ACK、terminalを含むヒストグラム区分の中点を使った。
区間計測では、pendingのみのキューp95はModel 3で432→528ms、
Model 4で456→434msだった。キュー待ちの改善は両モデルには再現していない。

## writerの区間計測

| 区間 | Model 3 A→B | Model 4 A→B |
|---|---:|---:|
| 観測検証・コピーの呼び出し | 14,784→4,928 | 15,480→5,160 |
| 観測検証・コピー CPU | 1.49→0.59秒 | 1.74→0.62秒 |
| pending合計 CPU | 16.26→15.87秒 | 17.12→16.92秒 |
| pending GIL保持の推定 | 15.31→14.99秒 | 16.03→15.89秒 |
| 15〜30秒のwriter CPU | 12.36→12.21秒 | 12.30→12.13秒 |
| 15〜30秒のJournal滞留中の推論空待ち | 4.44→4.43秒 | 3.33→4.08秒 |

区間計測は各条件1回。同じWriterでも呼び出し区間は入れ子で、
GIL保持は約1ms間隔のサンプルによる推定値。5〜15秒は変更後も推論
スレッドが9.85秒／10.00秒稼働した。15〜30秒はwriterにCPU負荷と
キュー滞留が残った。30秒以降はキューが縮み、残った試合が供給源となる。

保存Journalから採取した現行原本のフレーム508件／511件を再検証した。
原本JSONを一度組み立てた後、DecisionFrameの検証とハッシュ照合で
payloadをそれぞれ1回、JSONLへの投影で1回、再解析していた。
フレームの3回分のJSON解析はこのサンプルで合計約0.073秒／0.074秒。
以降を測る場合は、原本JSONの全体解析とフレームpayloadの解析を分け、
同じレコードの検証済みpayloadをハッシュ照合・投影で再利用できるか
を確認する。原本SHA-256と正規出力バイトの照合は必要。

実行記録は `runs/observation-reuse/` の `report.json`、`paired.json`、
`diagnostic-summary.json`、`trace-report.json`、`frame-parsing.json`。

## 正しさと採用

両モデルの3組すべてで収集時間が短縮したため採用した。
同じ実機StorageBundleを両方のwriterで処理し、Journal JSONL、候補列codec2、
両視点のReplayのバイト一致と、記録終了後のバッファ解放を確認した。
実同時256試合の12試行でも、各モデルの選択、記録FP32値、候補列SHA-256が
それぞれの基準試行と一致した。

回帰検証は384件成功、10件skip。既知の
[collector fixture不足](../issues/0012-rust-player-collector-cleanup-fixture.md)
の4条件を実行対象から除いた。初回の実行はCPUプロセスがTorchを見つけられず、
パッケージが実際のsite-packagesにある環境で再実行した。
Ruffと対象モジュールのmypyも通過した。
通常PPOとHPOは各16試合で更新1を保存し、再開後に16試合を追加収集して
更新2を確定した。optimizer stepはModel 3で16→28、Model 4で12→20。
初回と再開の全4実行でJournal・Replay・Python数値の完全監査が通過した。
保存時producerによる再開の照合は[ADR0057](../adr/0057-rust-ppo-training-data.md)
に従う。
