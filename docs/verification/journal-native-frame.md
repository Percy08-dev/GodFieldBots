# Journal フレーム検証の Rust 移行検証

2026-11-25、Bots 対照 `7a9e08135dea890d204533c468ae990515f265c0`、
Simulator `6d50603dab3f6d2df34ea4e433bab7dca96f52c1`。Gameplay API v2、
catalog `public-ja-v3` schema 2、共有 Sacrifice、Journal v6、候補列 codec v2、
SQLite group Pack v1、HPO Spec 6 / Run 5 / Update 8 / Collection 13。
CPU 側は CPython 3.14.10 の GIL 有効版、GPU 側は RTX 5070 Ti と
Torch 2.14.1+cu132。

## 比較方法

新規 HPO を1更新で一時停止し、seed 17、初期重み、自然終了256試合、Tokio
16 workers、推論幅32、形成待ち1 msを固定した。収集中の作業先は tmpfs、
確定先は専用 ext4。対照と候補はソースに対応した release wheel
をそれぞれ使った。対照→候補、候補→対照、対照→候補の3組で比較した。

全3組で収集 `actions/s` が改善し、中央値の差が対照3回の範囲を超えた段階を
採用する。分母の収集時間は記録の seal・永続化まで含む。実行全体の学習判断数/秒は
独立の指標。追加 p95 計時の試行は採否計時から外した。

標準の Pack・保存検証を通過し、Join 成功応答と終局 Action 到着の重なりから
全試行の実同時数256を確認した。各試行の5,081アクション、2,621学習判断を
論理試合・視点・判断番号で照合し、選択行動・FP32 log probability・value、
候補列の SHA-256、初期重みの SHA-256 の一致を確認した。

| 指標 | 対照 → Rust 検証 |

| 3組の収集 actions/s | 173.83 → 193.12 / 182.05 → 197.76 / 180.56 → 198.53 |
| 収集 actions/s の中央値 | 180.56 → 197.76（+9.53%） |
| writer スレッド CPU 時間の観測下限、中央値 | 20.01 → 18.31 秒 |
| 実行全体の学習判断数/秒、中央値 | 44.44 → 46.09 |

| pending の記録開始から受領 ACK までの p95、診断各1回 | 385.9–394.3 → 352.3–360.7 ms |

中央値差は17.20 actions/s、対照3回の範囲は8.21 actions/s。採用条件を満たした。
writer CPU と PSS は OS 観測の下限、Torch 予約はデバイス全体のメモリと別の指標。
この性能比較の適用範囲は固定 seed の初回更新。

- 現行 Sacrifice の元 StorageBundle を使う2つの成功ケースで、通常経路と
  作業領域不足時の Python 検証が同じ Journal・候補列・両視点の Replay を生成
  することを確認した。別の2ケースでは、有効な形式の誤った履歴 prefix と別原本の
  証明がそれぞれ Act の前に拒否された。
- Rust の対象2テストが通過。保存済みの初回181件・第75更新191件と12個の異常系でも
  Python/Rust の payload と判定が一致した。対象 Ruff、mypy（289ファイル）、
  diff の空白検査が通過した。
- 実 HPO の8試合予備試験で、両版の149行動の選択・FP32 スコア・候補列が一致し、
  Journal・Replay・学習配列の全量監査を通過した。
- 設計と独立した正しさのレビューを経た。対応する release wheel は拡張と監督バイナリを
  同ソースから作成した。作業領域の互換性を保つため、native 資源制限で検証できない
  レコードには既存 Python 検証を使う。期限と原本所有・候補検証は同じ経路で適用する。

採用コミット `5a601b3` で通常 PPO と HPO を実 GPU で各8試合・保存・一時停止し、
同じビルドから各8試合を追加収集して2更新目を確定した。4操作すべてで
Journal・Replay・Python による学習配列の全量監査を通過した。通常 PPO は
267件と111件、HPO は149件と99件の受理済みアクションを記録した。

## 第2段階　試合ワーカーでの事前検証

同じフレーム検証を、原本 pending のシリアライズ直後と FIFO ID 付与の間に置く
候補を比較した。検証結果は元の mailbox Entry から一度だけ消費し、SQLite 確定
と試合内の照合は writer が担当する構成とした。第1段階を対照とした6試行すべてで
256試合が実同時稼働し、標準監査と各行動・数値・候補列の照合を通過した。

| 指標 | 第1段階 → 並列候補 |
| --- | ---: |
| 3組の収集 actions/s | 194.40 → 195.72 / 197.15 → 197.68 / 192.65 → 199.00 |
| 収集 actions/s の中央値 | 194.40 → 197.68（+1.69%） |
| writer スレッド CPU 時間の観測下限、中央値 | 18.38 → 17.31 秒 |
| 実行全体の学習判断数/秒、中央値 | 45.55 → 45.21 |
| プロセスツリーの観測 PSS ピーク、3回の最大 | 3,227.6 → 3,214.9 MiB |
| 収集中の Torch 予約ピーク、3回の最大 | 442 → 470 MiB |
| pending の記録開始から受領 ACK までの p95、診断各1回 | 352.3–360.7 → 293.6–302.0 ms |

3組とも速くなったが、中央値差3.28 actions/sは対照の測定幅4.50 actions/sを
下回ったため見送った。診断では5,081件すべてで事前検証結果を一度だけ利用した。
ワーカーで計時した検証の壁時間の合計は3.20秒。並行処理が重なる各区間の累積値。

対象の Rust テスト18件が通過し、1件は保存済み原本用の明示実行テストとして
ignore。関連 Python テスト25件、現行 Sacrifice の実ケース5件が通過した。
期限切れによる全体停止、取消後に原本ビューが残る場合の解放、native 終了確認と
推論サービスエラーが重なった場合の workspace 返却を独立レビューで確認した。
実 HPO の8試合予備試験は、対照・第1段階と同じ149アクションで全量監査を通過した。

採用版の最終回帰確認は48件通過、21件 skip。
