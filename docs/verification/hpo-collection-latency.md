# 収集時間の詳細調査

## 結論

26.373秒は1試合の時間ではなく、32試合を同時2試合で実行した区間の
和集合だった。新しい詳細計測でも、1試合の平均は1.506秒、中央値0.918秒、
p95 3.506秒、最大7.265秒。収集全体は26.700秒で再現した。

試合の経過時間は、Simulatorの計算だけでなくActor準備、方策選択、IPC、
API往復、保存と終了を含む。今回、試合内の未分離時間を延べ0.850秒
（全試合延べ時間の1.764%）まで減らした。batch完了待ちは後段の学習更新側で、
この収集時間には含まれない。アプリ本体・ルール・学習計算は変更していない。

CPU時間だけを表すものではない。各試合内では入れ子区間を重複除去している。

### 長い試合と初期化

最長の`b000001-p2-seat1`は38行動、7.265101秒。そのうち選択・journal・captureが
6.603541秒（約91%）で、Actor準備は0.026825秒。長い試合の主因を初期化だけで
説明することはできない。既存decision timerでは、この試合の候補生成が
1.595164秒、方策選択が1.619187秒、worker往復差分が1.167933秒である。

一方、Actor準備は最初の収集に延べ6.340998秒、2回目は0.277652秒。
試合ごとの準備は中央値0.018014秒、最大1.633959秒で、初回側に偏る。
この計測はinitialize／再利用をまとめた区間であり、物理spawnとRESETを個別には
分離していない。従来のmodel_startup_msは開始からreadyまでの重複し得る値なので
合算には使わなかった。

## 既存のサーバーHTTPログによる照合

検証済みv2の最初のMLP C runから、GroupPack内の16HTTPログを検証済みreaderで
読み、本文・header・queryを出力せず安全なscalarだけ集計した。
3346request/response組、未対応0、HTTPエラー0、要求本文113,447bytes、応答本文
12,626,788bytes。Observe1145回、Act／Events／ActionOptions各611回、Replay64回、
Create32回、Join64回、Delete32回など。attest80回、catalog48回、public info48回もある。

サーバーのduration_msは整数ミリ秒への切捨てで、3293件が0、53件だけ非0。
記録上の合計90msはすべてReplay系だった。これはCPU時間ではなく、外側の要求本文
buffering後から応答capture完了までのmiddleware wall。小数ミリ秒が落ちるため、
「サーバーが合計90msしか処理していない」という結論には使えない。
この既存runのサーバー値を今回の別runのクライアント値から引くこともしない。

## 計測自体の影響と残る限界

| 指標・秒 | 従来の計測 | 詳細計測 |
| --- | ---: | ---: |
| collector呼出し2回合計 | 26.206947 | 26.692419 |
| helper全体 | 39.571549 | 37.814041 |
| インタプリタ・最終出力も含むプロセス全体 | 40.403898 | 39.024361 |

collectorは詳細計測側で0.485472秒（約1.85%）長かったが、1組だけでは
計測負荷と実行変動を分離できない。全体が短かったことを高速化や負の負荷とは
解釈しない。詳細spanは入れ子構造を保って、実際の終了確認後にだけ保存した。

未分離の0.849857秒にはactor／journalの構築、ACK後の制御、worker論理close等が
含まれ、そこを特定の処理へ推測で配賦しない。HTTPやworker往復の長い待ちが、
他の試合の同期処理によるイベントループ待ちか、転送／decodeかをさらに分ける
には、次段階の限定計測が必要。今回、コードの高速化・検証の省略・バッチ予算の
縮小は行っていない。batch完了待ちは後段のlearner更新／同期／入力view解放ACKの
区間で、収集の上記時間には含まれず、snapshot保存はそのACK発行後に続く。
