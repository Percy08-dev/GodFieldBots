# ライブJournal writerのイベントprefix照合の導入検証

基準は `aae33d3`。実行条件はSimulator
`072dabbca1458c9526897781d2fd64edeeb4f9ca`、Journal v6、codec2、
CPython 3.14.10、Torch 2.14.1+cu132、RTX 5070 Ti。
通常PPOのModel 3とHPOのModel 4を、各モデル同じseed 17、
初期checkpoint、実同時256試合で比較する。
GPU推論1レーン、形成待ち1ms、Tokio worker16、最大幅32、
推論一時領域128MiB、CUDA Graph形状 `(32,64,16)`。

実装の対象は、ネイティブのライブwriterの内部に限定した。
各イベントは追加時に検証・エンコードし、prefixハッシュを計算する。
追記の後は、同じ所有者・レイアウトおよび終端境界を持つことを確かめ、
フレームが参照する開始ハッシュを保持済みprefixに照合する。
公開ビューと保存済みデータの読取では、従来どおり履歴を検証する。

## 正しさの検証

実Simulatorの同じ不変 `StorageBundle` を両経路に渡し、
Journal JSONL、Replay、候補列バイナリをバイト比較した。
ライブ経路の試験では履歴ビューの再構築を禁止した状態でも、
各pendingからterminalまで同じバイトを生成した。
別の障害試験はFrame SHA、対応する候補表SHAを再計算してから
誤った開始ハッシュを提示し、開始ハッシュ照合で拒否されたこと、
候補列・decisionの公開とACKの前に失敗しsealされないことを確認した。

関連の標準pytestは530件が通過した。
既知のcleanup fixture不足4件は従来の選別に従った。
Ruff、mypy、差分チェック、独立した設計・実装適合および正しさレビューも通過した。
既知のfixtureについては [issue 0012](../issues/0012-rust-player-collector-cleanup-fixture.md) に記録する。

## プロファイラなしの反復A/B

HTTPのJoin応答から終局Actの到着までの重なりを使い、実同時256試合を
確認した各条件3試行を集計した。早く終局する試合が最後のJoinより先行して
実同時254〜255だった試行は保存し、同じ設定で再試行した。

| モデル | 方式Cの3試行 | 本実装の3試行 | 収集秒中央値 | 試合毎秒中央値 | 短縮 |
|---|---|---|---|---|---:|
| 3 | 33.38 / 32.74 / 32.42 | 30.12 / 29.60 / 29.32 | 32.74 → 29.60 | 7.82 → 8.65 | 9.6% |
| 4 | 34.77 / 34.79 / 34.52 | 31.06 / 31.24 / 31.02 | 34.77 → 31.06 | 7.36 → 8.24 | 10.7% |

| 指標の中央値 | Model 3 | Model 4 |
|---|---:|---:|
| Journal登録から取り出しまでのp95 | 466 → 398 ms | 474 → 407 ms |
| Journal最大キュー件数 | 229 → 228 | 224 → 226 |
| 推論要求毎秒 | 117.9 → 130.4 | 116.8 → 130.8 |
| forward数 | 919 → 906 | 909 → 924 |
| 有効要求/forward | 4.20 → 4.26 | 4.47 → 4.40 |
| ホストCPU時間 | 55.63 → 52.21 s | 59.34 → 55.90 s |

各モデルで初期checkpointのSHA-256が一致した。全12試行を照合し、
Model 3の4,928件とModel 4の5,160件について、候補列バイナリ、
選択行動、FP32 log probability・valueの一致を確認した。
同じ不変原本から生成したJSONLのバイト一致は別の実Simulator試験で確認した。

通常PPOとHPOは本実装で保存・一時停止し、再開後に16試合を追加収集して
2回目のPPO更新とJournal・Replay・数値の全量監査を通過した。
optimizer stepはModel 3で16から28、Model 4で12から20に進んだ。
Model 3は本実装の256試合の独立した全量監査も通過した。
Model 4は既存の12GiBの監査範囲に従い、256試合で封印済みPack照合、
保存と再開の16試合で全量監査を行った。

## Writerと推論サービスの再測定

別枠で旧・新各モデルの実同時256試合を測定した。
GIL保持は同じCPython ABIのネイティブサンプラーがpending中を約1ms周期で観測し、
保持割合と累積Wallから推定した。
writerの区間別CPUは、個々のレコードのスレッドCPU時間を集計し、
5秒境界をまたぐ記録をWall時間で按分した。グループ確定も含む。

| 指標 | Model 3 旧 → 新 | Model 4 旧 → 新 |
|---|---:|---:|
| pending Wall | 19.38 → 16.18 s | 20.81 → 17.11 s |
| pending スレッドCPU | 19.01 → 15.74 s | 20.39 → 16.59 s |
| pending 推定GIL保持 | 18.09 → 14.75 s | 19.34 → 15.62 s |
| 15〜30秒のwriter CPU | 12.61 → 12.29 s | 12.52 → 12.16 s |
| 15〜30秒のうちJournalが残ったまま推論が空待ち | 4.20 → 4.42 s | 3.08 → 4.27 s |

5〜15秒は導入後も推論サービスの処理中時間が9.88秒と10.00秒。
Eager forwardの累積ホストWallは7.52秒と7.99秒、推論スレッドCPUは
1.59秒と1.46秒だった。代表形状は候補128・イベント16と候補2,048・イベント16。
CUDA Eventの中央値は10.74msと12.97msで、サンプル数は20件と16件。
この区間はCUDAストリーム内の空白を含む。

15〜30秒には両モデルとも5秒あたり3.84〜4.29秒のwriter CPUが残った。
5秒区間ごとの平均Journalキュー深さはModel 3が38〜157件、
Model 4が61〜174件だった。前半はEagerを含む推論サービスが制約となり、
後半はJournalを処理して試合を再開するまでの待機が要求供給を引き続き制約する。

## 次のEager PoC

隔離測定では、両モデルの実験に使った初期checkpointから
元のarchitectureと重みを読み、重みのSHA-256を照合した。
バッチ幅32、有効行4件、異なる候補長・イベント長とPaddingを混在させた。
入力は既存の数値fixtureから拡張した。
プロファイラなしのホスト時間と、別呼び出しのCUDAカーネルトレースを
分けて記録した。

| モデル | 候補数・イベント長 | ホストWall中央値 現行 → one-hot統合 | カーネル数 現行 → 統合 |
|---|---|---:|---:|
| 3 | 128・16 | 4.14 → 3.54 ms | 510 → 364 |
| 3 | 2,048・16 | 6.54 → 5.20 ms | 648 → 502 |
| 3 | 2,048・0 | 4.88 → 4.21 ms | 466 → 377 |
| 4 | 128・16 | 4.85 → 3.82 ms | 512 → 366 |
| 4 | 2,048・16 | 6.47 → 5.17 ms | 650 → 504 |
| 4 | 2,048・0 | 4.92 → 4.31 ms | 468 → 379 |

次のPoCには、Eagerの状態・カード・イベントのone-hotをフィールド別に
生成し、FP32に変換して連結する部分の統合を選ぶ。
フィールド幅に応じた保持済みオフセットを使い、最終FP32バッファに
一度のscatterで同じ表現を作る。イベント長16ではこの部分の
カーネルが158から12に減った。6形状すべてで
log probability・確率・valueのFP32ビットが一致し、
各形状16件の抽選で選択行動と次のRNG状態が一致した。
これは隔離入力での結果。実収集での短縮幅は次のPoCの評価対象となる。

イベントGRUのcuDNN経路は、隔離測定でGRU区間のカーネルを115から11に
減らした。valueに最大約 `3.58e-7` の差が生じるため、
現在のビット一致条件ではone-hot統合を先に評価する。
候補スコアのチャンクを256から512に広げる案は、
幅32・候補2,048で最大一時テンソルの見積もりが
Model 3で144MiB、Model 4で216MiBとなり、現在の128MiB上限を超える。
今回のEager実装変更は隔離用スクリプト内に限定した。

再現用のコマンドと生ログは `runs/owned-bank-production/` に保存した。
通常A/Bは `report.json`、writer区間は `writer-report.json`、
5秒単位の比較は `trace-report.json`、隔離比較は `eager-shortlist.json`。
