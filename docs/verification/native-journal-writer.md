# RustのJournal候補検証とcodec2の導入検証

比較基準は `d7b736d`。Simulatorは
`072dabbca1458c9526897781d2fd64edeeb4f9ca`、共有CardInstance、
Journal v6、codec2を使用した。RTX 5070 Ti、CPython 3.14.10、
Torch 2.14.1+cu132で、通常PPOのModel 3とHPOのModel 4を個別に計測した。

1更新256試合、実同時256試合、seed 17、Tokio worker16、GPU推論1レーン、
形成待ち1ms、幅32、推論一時領域128MiB、CUDA Graph形状 `(32,64,16)`。
初期checkpointのSHA-256はモデルごとに一致する。標準wheelが同じソースから
native拡張とsupervisorをビルドしたことを、起動時のmanifestとSHAで確認した。

## メモリとPyO3

元の `StorageBundle` は既存の記録台帳で計上されている。
Rustはその連続バイト列を借りる。Rustの型付き列とフレーム配列は、
従来からあるwriterのprivate作業領域を使う。
Rust出力Vecの割当後に検証用の列が退役する。その後、Rust出力Vecと
Python `bytes` が重なる区間を既存のRecordingBudgetで計上し、
書き込み後は保持する候補バイナリの分を残す。
選択行動の一時JSONはprivate作業領域に含まれる。

| 形状 | 借用する元バイト | Rustの型付き列容量 | フレームVec容量 | codec2出力容量 | 出力の同時生存データ |
|---|---:|---:|---:|---:|---:|
| 1,447候補×18参照 | 164,894 B | 188,416 B | 576 B | 92,622 B | 185,244 B |
| 65,536候補×18参照 | 7,476,914 B | 7,602,176 B | 576 B | 4,194,312 B | 8,388,624 B |

既存プロトコル上限の候補表を含む構造テストで、実際のVec容量を測定した。
型付き列とcodec2出力が同時生存する区間と、Python側へのコピー区間には
時間差がある。表の同時生存データはコピー区間のペイロードであり、
アロケータの管理領域やPythonオブジェクトヘッダは別である。

## 正しさと再開

有効な全12試行でJournal JSONLが正規JSONであることを読み直し、
候補列のSHA-256と、選択行動・FP32 log probability・valueのビットを比較した。
Model 3は4,928件、Model 4は5,160件で一致した。
同じ実行時の元バンドルを旧・新writerに渡す試験では、8件のpendingとACK、
terminalから生じた候補列、Journal JSONL、Replayなど13ファイルがバイト一致した。
Rustのテストは全行の検証と正規ハッシュ、不正な未選択行と位置配列表の拒否を含む。
Pythonの実Simulator試験で、未対応プロファイルの経路選択、コマンド不一致、
書き込み障害、ACK前の失敗と予約返却を確認した。

通常PPOとHPOの両方で、旧環境の一時停止runのcheckpointを新環境で読み取り、
Journal・Replay・数値を全量監査した。producerが異なる新環境からの再開要求は
既存の一致検査で拒否され、run状態とcheckpointのSHA-256は変化しなかった。
旧環境で再開すると16試合を追加収集して更新が完了した。
新環境で開始したrunも同じ新環境で再開して追加16試合と更新を完了した。
optimizer stepは、両環境でModel 3が16から28、Model 4が12から20に進んだ。

Model 3は256試合のJournal・Replay・数値全量監査も旧・新で通過した。
Model 4の256試合には、既存の12GiB監査上限が適用される。
前回の方式C比較でその上限に達したため、今回は256試合で封印済みPackを照合し、
保存と再開の各16試合で全量監査を行った。監査予算の変更は伴わない。

Rustテスト4件、関連pytest 529件が通過した。
既知のfixture不足4件は従来どおり選別した。Ruff、mypy、差分チェックも通過した。
既知のテストは [issue 0012](../issues/0012-rust-player-collector-cleanup-fixture.md) に記録されている。

## 導入後のwriterと推論の負荷

導入版のコピーにだけ計測を追加し、両モデルの実同時256試合を別々に
観測した。RustとPythonの時刻は同じLinuxの単調時計を使う。
推論処理中はRustのバッチ取り出しからPythonの結果返却と解放まで。
推論の空待ちは、推論処理中以外でキュー深さがゼロの区間。
writerの処理時間は元Journalのエンコードとグループ確定を含む。
いずれも区間の定義によるWall時間で、別スレッドの区間は重なる。

| 指標 | Model 3 | Model 4 |
|---|---:|---:|
| 診断時の収集 | 32.51 s | 33.77 s |
| Writer処理中 | 23.24 s | 24.66 s |
| pendingの累積スレッドCPU | 17.60 s | 18.81 s |
| 全pendingのRust候補処理とPyO3の累積Wall | 0.70 s | 0.73 s |
| 推論処理中 | 21.33 s | 22.59 s |
| 推論キュー空待ち | 10.31 s | 10.46 s |
| そのうちJournalキューに要求がある時間 | 5.65 s | 5.91 s |
| Eager forward呼び出しの累積Wall | 13.33 s | 13.59 s |
| CUDA Graph forward呼び出しの累積Wall | 0.63 s | 0.65 s |

5〜10秒の推論キューの平均深さは181件と192件で、推論サービスは
両モデルで5秒間処理中だった。10〜15秒も4.74秒と4.99秒処理中だった。
この時間帯の推論側ではEager forwardが累積Wallの大半を占める。
CUDA Eventのサンプル中央値はEagerが約29.0msと16.5ms、
Graphが約1.77msと2.03ms。Event区間はCUDAストリーム内の空白を含む。

15〜30秒は、どの5秒区間でもwriterが約4.1〜4.5秒処理中で、
Journalの平均キュー深さは39〜175件だった。
推論は5秒あたり1.2〜2.2秒空待ちし、その時間にはJournalの要求が残っていた。
この時間帯には、Rustへの移管済み区間よりもwriter全体の残りのCPU処理が
要求供給を制約している。序盤の推論サービスと、中盤以降のJournalの処理を
別の制約として扱う。

実収集の最大codec2出力は、Model 3で1,714,858 B、
Model 4で712,409 B。PyO3から返るPython `bytes` の実サイズは
それぞれ1,714,891 B、712,442 Bだった。元バンドルの入力は借用した。

生ログと再現手順は `runs/native-writer-production/`。
通常A/Bは `report.json`、時間帯とメモリの診断は `trace-report.json`、
バイト比較は `sidecar-parity.json`、保存・再開証跡は `resume-*` にある。
