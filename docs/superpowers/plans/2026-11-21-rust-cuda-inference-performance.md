# Rust PPO収集のCUDA推論改善計画

> 実験は独立した作業領域で実施する。製品実装に進む場合は、設計レビュー後に `superpowers:subagent-driven-development` または `superpowers:executing-plans` で対象を順に実装する。

**目的**　PPOの学習条件を維持し、256試合の収集時間と試合数/秒を改善する。推論応答p95とメモリの実測も判断に使う。

**基準設計**　[RustのCUDAバッチ推論](../../design/rust-player-cuda-batch-inference.md)と[ADR0059](../../adr/0059-rust-player-cuda-batch-inference.md)。実験では同一の一括起動方式、256試合、同時256試合、GPU固定幅32、形成待ち1 ms、候補数 `64×2^n`、正のイベント長 `16×2^n`、イベント0件の独立区分を使う。ワーカー数比較以外はTokio 64ワーカーとする。同一モデル内で checkpoint、seed、精度、Simulator `072dabbca1458c9526897781d2fd64edeeb4f9ca`、ハードウェアを固定する。各試行で自然終了と実際の重複数を確認する。

**境界**　Rust は元のバッチの応答を一括検証・確定する。部分返却は計測対象とする。行動抽選、PPOのforward/backward、学習・保存の64 MiB制約は基準条件に含まれる。採用候補は、プロファイラを外した256試合A/Bを順番を入れ替えて各3回比較する。新しい計算形状やストリームでは、参照との許容差と、同一方式内の他要求への非依存性・抽選状態のビット一致を別に検証する。

## 実施順序

1. **推論一時領域の128 MiB試験。** 計測用コピーの `RustPlayerInference.bind_collection` でバッチ推論の一時領域だけを128 MiBまで受け付ける。`estimate_batch`、学習器・推論重みの常駐領域、CUDAコンテキストとcuBLAS作業領域の合計判定を使う。両モデル各256試合で64 MiBと比較し、逐次件数、H2D/D2H・同期、収集時間、ピーク割当と予約を記録する。コピー回数のコード由来の集計とCUDAトレースの観測値を区別する。上限超過が残る場合の縮小幅は、収集開始時にcheckpoint・形状・容量から決定する。同席件数を幅の決定に使わない。
2. **待機時間の計測。** Rustの投入・取り出し、各グループの推論開始・D2H完了、元バッチの返却を対応付ける。GPU→CPU転送のグループ単位と、Rustへの返却のバッチ単位を分けて記録する。部分返却の採否は待ち短縮と追加コストを比較できるまで保留する。
3. **CUDA Graph PoC。** 頻出形状 `(32,64,16)` の推論forwardで、Eager、`torch.cuda.CUDAGraph`、`torch.compile(mode="reduce-overhead")` を個別に測る。ウォームアップ、構築、定常時のCPU投入時間、CUDA Event区間とカーネルトレース、追加割当・予約、損益分岐forward回数を記録する。MLP Model 3・4の参照一致と独立性、同一アドレスへの重みコピー、新しいcheckpointのモデルで挙動を比較する。GRU・Transformerは現在の共有MLP実行経路と区別して適用条件を評価する。短いtrialと並列trialの判断は、構築頻度、実際の有効再利用回数、Graphごとの追加常駐量を使う。
4. **Tokio 16対64。** 初回は64 MiB、採用後は128 MiBの同一実行経路で、各モデル256試合を比較する。プロセスとTokioワーカーのCPU使用、候補探索のサンプル、収集時間とp95を確認する。差に応じて8・32を比較する。GPU待ちは現行の非同期応答と専用推論スレッドを使う。
5. **単一computeストリーム。** 転送ごとのホスト同期を取り除く効果を独立に測る。pinned memoryと完了イベントを使う場合、読み書き・再利用・退役を完了に結び付ける。
6. **転送と計算の重複。** 実測で必要になればcopyストリームとcomputeストリームを分け、二重バッファの費用と効果を比較する。
7. **2 computeストリーム。** Graphと単一ストリームの結果を確かめてから、1プロセスで同じ重みを使う形を比較する。同時生存バッファ、作業領域、完了イベント、決定論と応答の対応を検証する。

## 初回の作業と採用判定

- [x] 両モデルで、64 MiB/W64・128 MiB/W64・64 MiB/W16を各1回実行し、256試合の比較を記録する。
- [x] CUDA Graphの単体PoCを実行し、重みのアドレスと再利用回数による制約を記録する。コンパイル試験は直接キャプチャから分離する。
- [x] 計測結果を比較し、次に3回反復する候補と、追加調査が必要な項目を決める。

各試験で元の応答対応、イベント0件、隣接行に対する出力と抽選状態の独立性、checkpoint切替を確認する。失敗した試験も、条件と理由を記録する。製品化では、保存・再開、旧世代の失効応答、Journal・Replay照合と中断時のGPU完了・バッファ退役を加えて確認する。性能差の採用判断にはEager対照を使い、計測間の変動と単体試験の範囲を明記する。

## 初回の結果と次の比較

各行は各設定1回。6試行で自然終了256件、同時稼働ピーク256、同じ初期重み・承認済み行動数・推論要求数を確認した。標準の封印済み原本検証も通過した。

| 比較 | Model 3 | Model 4 |
| --- | --- | --- |
| 64 → 128 MiBの収集時間（W64） | 52.55 → 51.91秒 | 56.38 → 56.13秒 |
| 64 → 128 MiBの逐次件数 | 351 → 0 | 321 → 0 |
| 64 → 128 MiBのTorchピーク予約 | 118 → 262 MiB | 166 → 328 MiB |
| 64 → 16ワーカーの収集時間（64 MiB） | 52.55 → 51.76秒 | 56.38 → 56.21秒 |
| 固定形状のEager → 直接Graphの同期込みforward中央値 | 4.204 → 0.875 ms | 4.215 → 0.989 ms |

128 MiBで逐次経路の転送・同期が減り、応答p95も下がった。収集時間の短縮は約0.4〜1.2%だった。16対64ワーカーの差も1.6%未満で、収集中のTokio系スレッドの平均CPU使用量は約0.44コア相当だった。8・32ワーカーの比較は、16対64の差を反復で確認してから判断する。

直接Graphは、頻出1形状に限った収集A/Bに進める候補とする。固定形状の単体試験では、同席の値・長さ・位置・順序に対するビット一致と抽選状態の一致が通過した。キャプチャは14.5／7.2 ms、追加予約は44／54 MiBだった。損益分岐は同じウォームアップを既に支払った場合5／3回、初回準備をすべて追加費用とした場合181／102回だった。現行のcheckpoint公開は別アドレスの不変モデルを作る。最初の収集A/Bでは、各checkpointでのキャプチャ費用と退役を計上する。Graphの選択は事前に固定し、他要求の到着数で選択を切り替えない。

`torch.compile` の全体トレースはイベントGRUで停止した。グラフ分割を許したModel 4の追加試験はCUDA Graphの起動を観測したが、初回forward約11.5秒、定常の同期込み中央値4.28 ms（Eager 4.26 ms）、追加予約100 MiBだった。GRU・Transformerの合成固定長ブロックは直接キャプチャできた。試合入力、可変履歴、状態/KVキャッシュを持つ両アーキテクチャの収集経路には独立の評価が必要となる。

元バッチの全結果を返す既存の通知方式を継続する。D2Hは現在も各グループで行う。投入から各グループ開始までと、グループ完了から元バッチ返却までを分離した本番条件の時系列計測を残作業とする。

実行設定、標準ベリファイ、CPUサンプル、転送回数の算出、Graphの試験結果は `runs/cuda-batch-inference.kYXk2q/min-candidates32.i6NCPk/buckets-64-16.2mhj80/width32.Zl6yqI/next-optimizations.zVIMMa/` に保存した。

## 2026-11-22に承認された実施順序

- [x] `RustPlayerInference.bind_collection` でCUDAバッチ推論の一時領域を128 MiBまで受け付ける。モデルが64 MiB未満を指定している場合は、その指定を使う。従来の総容量判定を適用し、学習・保存の64 MiBは同じ検証で確認する。既存テストと標準検証で採用する。
- [x] 採用後の128 MiBでTokio 16対64をModel 3・4の各256試合で比較する。各条件1回で、64→16の収集時間はModel 3で51.58→51.17秒、Model 4で56.74→56.62秒だった。Graph比較には16を選んだ。
- [x] 実測の頻出形状 `(32,64,16)` だけを対象とした直接CUDA Graphを計測用コピーに組み込む。収集中は同一checkpointを使い、対象外はEagerで処理する。元のRustバッチの一括返却を使う。
- [x] 同じ環境でModel 3・4のEager／Graphを256試合で交互に各3回実行する。キャプチャ、再生回数、メモリ、要求と抽選の独立性、新しいcheckpointでの重み反映を確認する。待機の集計では、Rust投入、forward投入、CPU側の出力到着、Rust一括返却の各境界を明記する。
- [x] 実際の形状別forward回数と準備コストから、256試合と、同一checkpointを4回の収集で使う1024試合の純短縮時間を試算する。暖機を含む場合と、モデルが既に暖機済みの場合を分け、追加候補は形状別の短縮見込みと共存メモリで比較する。

Graphの実収集比較は、既存のC256計測用一括起動・区分を使う。同時実行数設定と観測した同時数をそれぞれ残す。Graph導入のためのcheckpoint公開方法、更新単位、推論ストリーム数の変更は、今回と別に判断する。

### 頻出1形状の実収集A/B

RTX 5070 Ti、128 MiB、Tokio 16、固定幅32、形成待ち1 msで各モデル3組を交互に実行した。Model 3はEagerから、Model 4はGraphから開始した。各試行で自然終了256試合、実際の同時稼働256試合、同じ初期重み、同じ行動・推論件数、逐次fallback 0件を確認した。全12試行で標準の封印済み原本と更新後の保存データの検証が通った。収集時間はGraphの準備と退役を含む。PPO更新時間は別に集計した。

| 指標 | Model 3 Eager → Graph | Model 4 Eager → Graph |
| --- | ---: | ---: |
| 収集時間 3試行（秒） | 52.96 / 52.61 / 51.19 → 50.26 / 49.35 / 49.73 | 57.79 / 57.71 / 56.59 → 54.07 / 55.09 / 54.96 |
| 収集時間中央値（秒） | 52.61 → 49.73（5.5%短縮） | 57.71 → 54.96（4.8%短縮） |
| 試合数/秒 | 4.87 → 5.15 | 4.44 → 4.66 |
| 全forward数の中央値 | 662 → 1,144 | 666 → 1,281 |
| `(32,64,16)` のforward数の中央値 | 399 → 869 | 406 → 1,011 |
| 有効要求数/forward | 5.83 → 3.38 | 6.10 → 3.17 |
| 集約した応答p95（秒、ヒストグラム区間） | 4.56–4.70 → 4.83–4.97 | 4.97–5.10 → 4.83–4.97 |
| 収集中のTorchピーク割当（MiB、3試行の最大） | 203.1 → 235.9 | 214.0 → 246.7 |
| 収集中のTorchピーク予約（MiB、3試行の最大） | 262 → 384 | 332 → 470 |

固定形状の単体校正ではforward投入からD2H完了の中央値が4.23 → 0.94 ms、4.29 → 1.03 msだった。実収集ではD2Hを含むforwardステージが34.69 → 22.45秒、37.49 → 23.60秒に短縮した。バッチの取り出し頻度が上がり、推論スレッドの `next_batch` 呼び出し時間の累計は5.36 → 11.42秒、6.20 → 12.64秒、CPU側の抽選処理は6.09 → 8.65秒、6.92 → 10.50秒に増えた。ステージ累計は同じ区間または別の実行主体と重なることがある。

GPUからCPUへの結果転送はグループごとに行う。各グループのD2H完了から元のRustバッチの返却までのp95は、グループを等しく数えると230 → 189 ms、260 → 191 msだった。要求単位では343 → 449 ms、405 → 493 msだった。Rustキュー投入からPythonのforward投入までのp50は104 → 45 ms、129 → 48 ms、p95は4.42 → 4.53秒、4.99 → 4.69秒だった。部分返却による収集時間の効果をこの測定からは推定できない。

別のModel 3の256試合収集では、CUDAトレース上の先頭カーネルとRustの投入時刻を24グループずつ照合した。要求投入から最初のカーネルまでのp50／p95は、Eagerで2.03／2.55秒（166要求）、Graph有効時で2.75／3.08秒（159要求）だった。各トレースの頻出形状5グループでは、カーネルの実行区間を合わせた中央値は0.88／0.81 msで、カーネル間の空白の中央値は142.94／0.21 msだった。採取した区間のGPU実行とホスト負荷を表す短い観測で、プロファイラを外した収集全体のA/Bや応答分布には含めていない。トレースと照合集計は `device-start/` にある。

参照との比較は `atol=rtol=1e-5` で通過し、隣接要求の値・長さ・位置・順序を変えた場合の抽選結果と次のRNG状態も一致した。実収集の同一条件1組ずつでは、対応する3,861件と4,063件すべての選択順番、FP32のlogprob、valueがビット一致した。各モデルで32試合ずつ2回の実PPO更新を行った検証では、更新後のcheckpointを参照する別のGraphでの再生と旧Graphの退役を確認した。

## 頻出1形状を製品経路に組み込む設計

- 通常PPOとHPOが同じランタイム宣言から `batched-torch-graph-v1` を明示選択する。既存レシピの宣言、形状、再開時の照合は従来の意味を保つ。Graphレシピでは実測と同じ候補 `64×2^n`、正のイベント `16×2^n`、イベント0の独立区分を使い、上限は既存の候補・イベント設定に従う。Tokioのworker数を省略した場合は16とし、明示された値と固定スケジューラの宣言も受け付ける。128 MiBは既存の推論バッチ専用上限を使う。
- 収集の管理側が現在の学習checkpointを専用の引数として推論サービスに渡す。Graphと固定テンソルの所有者はPython推論サービスに1件だけ置く。現在の収集の実物の不変重み、事前に許可された形状 `(32,64,16)`、検証済みのModel 3・4の構成に限定し、同席数や要求内容を見ずに選ぶ。対象外の構成・checkpoint・形状、追加常駐を収められない場合はそのレシピのEagerを使う。CPUは従来のスカラー経路を使う。
- 既存の直列Torch境界内で、actor起動前にダミー固定入力で暖機とキャプチャを行う。入力転送と出力転送、CPU側の要求単位の抽選は既存の順序に従う。CUDAの容量判定に静的入力と専用プールを一度ずつ加え、Eager/スカラーの既存経路が同じ予算で実行できる余地を保つ。実測した専用プールに対する判定を行う。新しいキャプチャ／再生操作の障害は既存の失敗所有者に保管する。発生の分かっている非対応条件はキャプチャ前に判定する。
- 一括返却後、既存のproducer停止とデバイス完了の境界でGraphと固定バッファを退役させる。更新・同じ重みを公開する既存の手順を使い、次の収集が新しいGraphを作る。checkpointとGraphをまたぐキャッシュは持たない。Simulatorの入力契約、Rust応答契約、保存形式を引き継ぐ。
- 推論結果と抽選、古いGraphの退役、予算によるEager選択、次のPPO世代の重み反映を検証する。効果の確認では同じ区分・seed・checkpointの256試合を計測し、形状ごとの要求総数とforwardを照合する。待機の区間は既存の計測用Rust／Pythonコピーに閉じた診断で確認し、GPUタイムスタンプは追加同期を入れず、範囲を限定して照合する。

設計レビューで、Graphの適用は検証した二つのMLP計算構成、１チャンクで候補64を処理する設定、修正版入力レイアウト、PyTorch 2.14.1・CUDA 13.2・native allocator・SM120に限定した。常駐量を推論キャッシュの重量と区別し、事前に許可したEagerおよび実際にスカラーへ回る形状の余地を保つ。製品の診断はGraphレシピ名と再生回数を保存する。保存済みの通常PPOおよびHPOの実効設定は正規化済みのワーカー値を検証する。

### 同一行動列におけるforward増加の内訳

PoCは共有する読み取り専用重みと独立したバッファを使用した。完了イベントまで送受信バッファを所有し、D2H済みの値を読み、再利用後もRustに渡すログを保持する。両モデルで元バッチ単位の応答、log probabilityとvalue、選択結果、次の乱数状態の一致を確認した。

同期基準の8グループの小規模トレースでは、H2D 24回・D2H 8回に対して `cudaStreamSynchronize` が32回あった。H2Dだけの非同期化では入力バッファごとの待ちを省き、同じStreamなので後続forwardとの順序を維持できる。D2H完了まで入力を保持する。1件ずつ結果を回収するPoCでは、pinned D2Hを発行した直後にEventを待っても処理率は482.2／459.0グループ毎秒で、H2Dだけ非同期の486.9／460.7を上回らなかった。pageableからpinnedへ余分にコピーする場合と直接pinnedへ詰める場合も比較した。

形成済み2バッチでは単一Stream上で前の完了を待つ前に次を投入した効果が確認できた。分離したcopy Streamおよび2 compute Streamでは、採取したトレースにforwardカーネル同士やcopyとforwardの重なりは見られず、1 compute Streamに対する追加改善は混合PoCでも0.5%未満だった。別computeを使う試作ではModel 3／4のTorchピーク予約が884／1172 MiB、共有computeで706／946 MiB、同期基準で572／618 MiBだった。複製したGraphの専用常駐は44.7／54.7 MiB。常駐量は静的入力と専用プールの和で、ピーク予約には動的な領域やallocatorが再利用用に保持する領域も含まれる。

確率正規化と指数化はGPUのforward内で実行する。CPU抽選は要求ごとにTorchのGeneratorでFP32確率から1件を選ぶ。現在のPyTorchは指数乱数を用いて選択し、CPU上でsoftmaxや累積確率計算を追加実行しない。抽選の計時はGPUの転送・同期を含まない。Wall時間とスレッドCPU時間との差の中で、個々の依存ライブラリの待ちを正確に帰属させる根拠は得られていない。PyTorch経路の検査と抽選を確認した一次資料は[対象版のATen実装](https://github.com/pytorch/pytorch/blob/5c4886908584029761b579af026dcfb627c84070/aten/src/ATen/native/Distributions.cpp#L545-L575)。

## 形成待ち1／4msと、同期推論2レーンの比較

### 既存経路とPoCの範囲

Rustの要求キューは未取り出し要求をFIFOで保持する。先頭の登録時刻に
`formation_wait_ms` を加えた期限か、最大幅32への到達で取り出し可能になる。
`Dispatcher::next_batch` が呼ばれた時点で元のRustバッチを取り出し、Pythonが
その中をcheckpoint・候補区分・イベント区分でグループ化する。条件成立済みの
要求も取り出しまでは同じFIFOにいる。4msの比較は既存パラメータで実施できた。
`next_batch` の条件変数待ち中、PyO3はGILを解放する。一方、Rustの `forming` は
同時の2呼び出し目を拒否する。複数の取り出し済みバッチを保持し、バッチID単位で
順不同に受理する機能は既存のRust経路にある。受理時の照合とRNG確定は各バッチに
対して行われる。

計測用Pythonコピーでは、`gf_simulator_client.rust_player.RustPlayerRuntime._serve`
の2スレッドが `next_batch` の周囲だけを排他し、同じRustキューから取得する。
各スレッドは元バッチ全体を採点して一括返却する。`gf_models.rust_player` は前処理、
H2D、forward、D2H、抽選の順を維持し、2本の専用Streamと読み取り専用の共有重みを
使う。 `RustPlayerDeviceAccount` の製品経路はGPU使用中の処理1件を保持するため、
PoCの評価区間では2件の実生存を合算する。既存のTorchロックは会計と公開・学習・
退役に用い、2レーンのforwardとブロッキングD2Hをまたいで保持しない。
CUDA Graphは両レーンとも同じ `(32,64,16)` で捕捉する。レーンごとに静的入出力、
Stream、専用プールを保持し、同じcapture Streamで再生する。cuDNN無効・数学SDPAの
設定は収集区間で揃える。2レーンの失敗時には、両スレッドの回収とGPUフェンスの
あとで実際に残った操作を退役させる。

前回のPoCは、形成済みの固定入力を1本のPythonスレッドから先行投入し、非同期の
コピーを含めてStream構成を比較した。今回のPoCは各レーンが実収集の同じキューから
処理を取得し、自分のD2H完了を同期的に待つ。両レーンの入力・Graphを同時に使うため、
前回エラーになった方式間のGraph再利用は避け、試行ごとにキャプチャを作り直した。

### 重いEagerと軽いGraphの同時投入

同じRust dispatcherで前後2つの元バッチを取り出し、候補2048・イベント0の
Eager forwardの投入開始を起点に、頻出Graphを別レーンに投入した。両モデルとも
12対の非プロファイル計測で、軽い要求の起点からCPU結果到達までの中央値は
Model 3が7.99 → 2.11ms、Model 4が9.16 → 2.09ms。両方の結果が揃うまでの
中央値は7.99 → 7.18msと9.16 → 8.64ms。全候補のlog probability、value、
選択行動、次のTorch RNG状態が1レーンと一致した。

別の5対のCUPTIトレースでは、軽いGraphの先頭カーネルが重いEagerのD2H完了より
中央値4.89／7.21ms早く始まり、GPUカーネル区間の重複は0.150／0.144msだった。
軽いGraphのD2Hも重いEagerより3.27／6.06ms早かった。ホスト投入と独立したGPU
実行の両方を観測した。トレース中のEagerカーネル間隔の和は6.66／6.45ms、
Graphは0.218／0.218ms。CUPTI付きの間隔は本計時から除外した。

### 2レーンの実収集で増えた処理

プロファイラなしの初回4条件では、同じ形成待ち幅の1レーンから2レーンにすると、
Model 3は3.52秒（1ms）と2.94秒（4ms）、Model 4は3.20秒と2.68秒遅くなった。
Model 3の1レーン・1msの初回のみ、HTTPから確認できた実同時稼働の保守的下限が
255試合であり、その条件は追加の同時256試合でも計測した。1msでCPU応答p95は
両モデルとも約4.0秒に縮んだが、元バッチを早く取り出すと一緒にforwardされる行が
減り、Model 3のforward回数は1,277 → 2,034、Model 4は1,351 → 2,253になった。
1msでのスレッドCPU時間の和は6.98 → 13.37秒、7.21 → 13.29秒。
元バッチの占有時間の和には重複があり、これを収集Wall時間の内訳には使わない。

4msで2レーンの充足は回復したが、同じ4msの1レーンよりforwardが多かった。
1msの2レーンのTorchピーク実割当／予約はModel 3が425／658 MiB、Model 4が
476／806 MiB。1レーン・1msの初回は236／384 MiBと246／388 MiBだった。
2番目のGraphの専用常駐は44.74／54.74 MiB、追加キャプチャは各試行21–25ms。
両レーンのGraph再生を計測し、4つの2レーン試行で両方の専用プール退役を確認した。
今回は収集時間の差と追加の会計・ライフサイクルの負担から、2レーンを見送る。
